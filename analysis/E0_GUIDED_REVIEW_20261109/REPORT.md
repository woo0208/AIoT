### 별도로 발견한 계측 경계

현재 한 루프의 실행 순서는 다음과 같다.

```text
Tk 안내창 poll: update_idletasks() → update() → 상태/문구 갱신
→ begin_receive → 센서 수신 → 정합 → Pose/Face → 특징·필요 시 집계/SVM
→ OpenCV 화면 생성/제출 → waitKey(1) → frame_completed
```

`e0_guided_panel.py:139`의 Tk update 계열 호출은 `posture_geometry_probe.py:2444`에서 begin_receive보다 먼저 실행된다. 기존 `ui.key_wait`도, 수신부터/수신대기 시작부터 frame_completed까지의 지연도 이 Tk poll을 포함하지 않는다. 전체 stream 시간과 FPS에는 포함된다. 따라서 기존51~53ms p95를 Tk까지 포함한 전체 UI 루프 p95로 부르면 안 된다. 저장 표의 수신 후 처리 경계는 그대로 보존한다. summary모드에는 시간표본의 원래 frame_id가 없지만, 두 완료 실행의 수신/처리 수와 주요 단계 수가 모두 같고 누락이 없어 순번을 대조했다. Tk poll 시각·duration은 없어 과거 전체 루프 지연을 소급 계산할 수 없다.

합성 SDK/가상 시계로 Tk poll500ms, waitKey100ms를 루프마다 주입한3루프 구조 검증을 수행했다. 실제 카메라/창 없이 기존 run_probe를 호출한 결과, ui.key_wait와 두 프레임 지연 p95는100ms, stream 시간은1.8초로 나타나 Tk1500ms가 프레임 지연에서 빠지고 stream에는 포함되는 경계를 재현했다. 이는 계측 경계 검증이며 실제 하드웨어 성능 결과가 아니다.

### 다음 개선 가설과 한계

단일 E1 후보는 지원되는 Win32 경로에서 `waitKey(1)`의 명시적 키 대기를 `pollKey()` 기반 이벤트 처리로 바꿨을 때 지연이 줄어드는지 검증하는 것이다. 공식 문서상 pollKey는 키 입력을 기다리지 않지만 GUI 이벤트는 처리한다. 따라서 창 이벤트 처리로 인한 장기 지연까지 사라진다고 보장할 수 없다. 키 반환값·Q 종료·Tk 자세 선택/취소 기능을 보존하고 E0/E1에 같은 화면/운영 조건을 적용해야 한다. 단순히 waitKey를 삭제하면 이벤트 처리가 달라지므로 권장하지 않는다.

그 전에 E0/E1 공통으로 Tk poll·전체 루프 경계를 관측할 필요가 있다. 기존 지연 필드는 유지하고 추가 계측은 양쪽에 동일하게 적용해, 계측 범위 변경을 성능 개선으로 보고하지 않아야 한다. 기존 E0 자료와 새 전체 루프 지표는 직접 같은 지표로 비교하지 않는다. 이번에는 해당 계측 추가나 pollKey 교체를 구현하지 않았다.

검증은 보존된 두 실행의 전체 파일 해시 확인, timing38군 재계산, 동일 순번 단계 대조, 현재 소스 경계 확인 및 합성 경계 검증1건 PASS다. 세부 증거는 `local_private/ui_latency_analysis.json`, 합성 결과는 `local_private/ui_latency_boundary_test.json`에 저장했다. 별도 회귀 테스트/실측·UI 실행·E1 구현·학습·Commit·Push는 하지 않았다. 공식8조합·B6·IRB 규칙과 기존 모델·특징·집계는 유지했다.

## 공통 계측 보완·단일 E1 구현 검증 (2026-11-09, 후속 요청)

사용자의 후속 구현 요청에 따라 E0/E1 양쪽에 동일한 Tk idle/update/전체poll, Tk 진입→프레임 완료, 전체 루프 계측을 추가했다. 기존 수신 후/수신대기 시작 후 지연은 유지하며 새 루프의 경계·표본 집합을 구분했다. 전체 루프에는 timeout·invalid pair·deadline skip·UI 종료·예외도 남긴다. 기존 bounded 로그 저장을 재사용하고 모델·특징·집계·적격 기준은 변경하지 않았다.

단일 E1은 `--variant E1`로 명시할 때만 waitKey(1)를 pollKey로 교체한다. 확인된Win32 backend/pollKey 지원이 없으면 카메라 시작 전에 실패하며 자동 fallback하지 않는다. 기본값 `--variant E0`는 waitKey(1)를 유지한다. 키/종료 동작은 같은 처리기를 사용하고 새 로그는variant와 공통timing contract를 기록한다. UI 창과 자세 진행은 양쪽에서 같다.

관련219개 테스트 PASS（기존208+신규11） 및 실제 SVM/Scaler artifact의 E0/E1 check-only PASS. 합성 입력에서 세 계측 모드와 두 variant의 특징·Scaler 입력·판정이 같았고, 주입한 Tk 지연이 새 지표에 들어가면서 기존 수신 후 지연 경계는 유지됨을 확인했다. 합성 시계 결과는 실제 지연 개선 수치가 아니다. 실측 p95/FPS/CPU/RAM 변화는 아직 NOT_MEASURED다. 세부 구조 검증은 `local_private/e0_e1_common_timing_validation.json`에 저장했다.

과거 완료 실행 A/D와 모델 자료는 파일 해시 그대로 보존했다. 새 공통 계측으로 소스가 바뀐 사실을 과거 실행 기록에 소급 반영하지 않는다. 새 전체 루프 성능을 비교하려면 새 E0/E1을 동일한 계측·운영 조건으로 실측해야 한다. pollKey도 GUI 이벤트를 처리하므로 기존 긴 지연이 모두 사라진다고 보장하지 않는다. 실제 카메라/사람 측정·재학습·Commit·Push는 하지 않았다. 변경 파일과 정확한 지표 경계/명령은 `E0_INSTRUMENTATION.md`의 후속 절에 기록했다.
